3. CTGAN — Synthetic Data Generation Method

MEASURED — CTGAN

CTGAN — Conditional Tabular GAN

CTGAN (Conditional Tabular GAN) is a generative model designed specifically for tabular datasets. It learns patterns from numerical and categorical columns and then generates new rows that follow the learned patterns. In this project, the synthetic HR dataset shown above was generated using the CTGAN plugin in SynthCity.

Actual HR data → CTGAN learns numerical + categorical patterns → generates new HR records → synthetic dataset → profiling → fidelity evaluation

What we used

  • Dataset: IBM HR Employee Attrition.
  • Actual dataset: 1,470 rows × 35 columns.
  • Synthetic dataset: 1,470 rows × 35 columns.
  • The synthetic file was then profiled using the same profiling workflow as the actual dataset.
  • The profiling results are compared in the next section for all 35 columns.

Why CTGAN is used here

HR data contains a mixture of numerical values such as Age, MonthlyIncome and YearsAtCompany, as well as categorical values such as Department, JobRole, Gender and BusinessTravel. CTGAN is intended to learn relationships across these different types of tabular values and create new records without simply copying the original rows.

Important: successfully generating 1,470 rows only tells us that the generation process completed. It does not by itself prove that the generated data has the same statistical properties as the real data. That is why the profiling and fidelity analysis below are performed separately.

Experiment flow: The CTGAN-generated CSV is the synthetic dataset used for the profiling comparison below. The profiling section therefore checks whether the generated data preserves the characteristics observed in the original HR dataset.

What the fidelity metrics mean

KS statistic: compares the distributions of a numerical column. Lower values mean the two distributions are closer.

KS p-value: a value ≥ 0.05 means this test does not provide strong evidence of a distribution difference at the 5% level. It does not prove the datasets are identical.

Chi-square: compares categorical frequency distributions. Lower values generally indicate less discrepancy.

TVD: total variation distance measures the difference between category proportions. 0 means identical proportions.

Human-readable deduction

The CTGAN output preserves several broad structural patterns, including zero missing values and many similar numerical/categorical ranges. However, the fidelity tests show noticeable differences for a number of columns, including some important HR fields such as Attrition, JobRole, MonthlyIncome, YearsInCurrentRole and YearsWithCurrManager.

Deduction: this particular CTGAN run produces usable synthetic-looking HR records, but the statistical evidence does not support treating the synthetic dataset as a close replacement for the real dataset across every column.

6. When to Use This Synthetic Data

  • Suitable for: development, demonstrations, dashboard prototyping, pipeline testing and exploratory analysis where exact employee records are not required.
  • Use with caution: analyses where accurate reproduction of attrition rates, job-role distributions, income distributions or long-term employment relationships is critical.
  • Before production use: repeat the benchmark with the exact downstream task, compare correlations and joint distributions, and validate whether the synthetic data supports the intended analytical conclusions.

LOCAL EXPERIMENT — AFFECTED BY COMPILATION / ENVIRONMENT

GReaT — Transformer-based Tabular Generation

GReaT uses a transformer/language-model style approach to learn how values in tabular records relate to each other and then generate new records.

Tabular rows → transformer representation → learned relationships → generated tabular rows

What happened in our environment

  • The experiment could not be turned into a clean standardized benchmark.
  • The environment had compilation/toolchain limitations, including the KeOps C++ / compiler dependency.
  • CUDA/GPU acceleration was not available in the environment, leaving the workload CPU-bound.
  • Because of these environment limitations, larger-scale transformer generation was not practical to benchmark fairly.

Why GPU/compilation matters

Transformer workloads perform many matrix operations and are normally much faster on a compatible GPU. Some dependencies used in the surrounding stack can also require native compilation. If CUDA libraries or a working C++ compiler are unavailable, the pipeline can fail before generation or fall back to much slower CPU execution.

Important: this is a limitation of our local setup, not proof that GReaT cannot generate synthetic data.

Deduction: GReaT needs a properly configured environment for a meaningful large-scale benchmark. Our local compilation and GPU limitations prevented us from treating it as a comparable measured result.
LOCAL EXPERIMENT — AFFECTED BY COMPILATION / GPU / DATA PREPARATION

DDPM / TabDDPM — Diffusion for Tabular Data

Diffusion models generate data by learning to reverse a gradual noise process. TabDDPM adapts this idea to tabular numerical and categorical data.

Real tabular data → add noise → learn denoising → start from noise → reverse denoising → synthetic rows

Problems encountered

  • The environment was CPU-only; CUDA/GPU libraries were unavailable.
  • KeOps reported that a C++ compiler / g++ / CXX was unavailable.
  • OpenMP/CUDA-related environment limitations were also observed.
  • A categorical preprocessing error occurred: “Class values must be non-negative”.

What the error means

The compilation problem means part of the computational stack could not build/use its native accelerated components. The categorical error is separate: the data encoding did not match what that implementation expected.

Therefore, we cannot fairly report a standardized DDPM runtime or fidelity score from this experiment.

Deduction: The DDPM/TabDDPM attempt was blocked by environment and preprocessing issues. The correct conclusion is “the local benchmark could not be completed cleanly”, not “diffusion models do not work.”

9. What We Actually Learned

  1. Generation success is not the same as fidelity. A model can generate the requested number of rows while still producing distributions that differ from the real dataset.
  2. Hardware and environment matter. Transformer and diffusion workloads can be heavily affected by missing CUDA support, native C++ compilers and related dependencies.
  3. Data preparation matters. The TabDDPM attempt showed that categorical encoding can prevent a run before model quality can even be evaluated.
  4. Runtime must be recorded separately. NeMo's 127.8 seconds describes one 10-record experiment, while no runtime was recorded for CTGAN and no clean runtime was established for the failed GReaT/DDPM attempts.
  5. Small tests do not prove scalability. None of the small successful tests should be presented as evidence of million-row performance.
  6. A fair comparison needs one benchmark protocol. The same dataset, same input size, same synthetic output size, same hardware, same preprocessing, same fidelity metrics and recorded training/generation/resource usage should be used.

11. Estimated Pros and Cons of Each Method

How to read this section: These pros and cons are estimated method-level characteristics, not additional measured results from the experiments above. Method-specific limitations are separated from common runtime, memory and hardware considerations so the same infrastructure limitation is not repeated for every method.
CTGAN

CTGAN — Estimated Pros and Cons

Pros

  • Designed specifically for tabular data containing both numerical and categorical columns.
  • Can learn non-linear relationships between columns and generate new combinations rather than simply copying rows.
  • Well suited to mixed business datasets such as HR, customer and transactional tables.
  • Synthetic output can be evaluated using familiar profiling and statistical fidelity checks.

Cons

  • Highly imbalanced categorical columns can be difficult to reproduce accurately, especially when some categories have very few examples.
  • Rare categories or minority patterns may be underrepresented or missed in generated data.
  • GAN training can be unstable and results can vary between training runs.
  • Mode collapse can reduce the diversity of generated records by concentrating on only part of the real distribution.
  • Good overall distributions do not guarantee that every individual column is reproduced equally well.
  • Complex relationships involving several columns may be harder to preserve than individual column distributions.
  • Hyperparameters and training configuration can noticeably affect synthetic-data quality.
  • Successful generation does not itself provide a privacy guarantee; privacy and memorization risk require separate evaluation.
GReaT

GReaT — Estimated Pros and Cons

Pros

  • Uses transformer-based modelling and provides an alternative to GAN and diffusion approaches.
  • Can represent complex relationships between fields through a language-model-style representation.
  • Useful for investigating contextual dependencies between attributes.
  • Provides a useful comparison point for transformer-based tabular generation.

Cons

  • Converting structured rows into a textual representation adds another modelling layer between the original table and generated data.
  • Output quality can depend strongly on how column names, values and records are represented as text.
  • Generated records may require post-processing and validation before being treated as valid structured data.
  • Strict numerical relationships and numerical precision can be harder to control through language-model generation.
  • Invalid or logically inconsistent combinations can be generated unless constraints or validation are applied.
  • Results depend partly on the behaviour and limitations of the underlying pretrained language model.
  • Rare categories and unusual combinations may still be difficult to reproduce reliably.
  • Rows may appear plausible without preserving the real dataset's statistical distributions, so fidelity testing remains necessary.
DDPM / TabDDPM

DDPM / TabDDPM — Estimated Pros and Cons

Pros

  • Provides a diffusion-based alternative to adversarial GAN training.
  • TabDDPM is designed specifically for tabular data.
  • Can model complex tabular distributions when numerical and categorical variables are represented appropriately.
  • Useful for comparing modern diffusion approaches with GAN and transformer-based methods.

Cons

  • Tabular datasets contain heterogeneous feature types, making joint modelling of continuous and discrete variables challenging.
  • Categorical and continuous variables require different treatment and careful preprocessing.
  • Discrete variables remain a difficult part of tabular diffusion modelling.
  • Mixed-type features can be especially difficult to represent correctly.
  • Output quality can depend on diffusion configuration and the selected noise/denoising process.
  • Rare classes and unusual regions of the original distribution can require additional attention.
  • Generated records still need validation for business rules and logical consistency.
  • Preprocessing or encoding mistakes can prevent training or lead to misleading synthetic output.
NVIDIA NeMo Data Designer

NVIDIA NeMo Data Designer — Estimated Pros and Cons

Pros

  • Provides a configuration-driven workflow for controlled synthetic-data generation.
  • Useful for text-rich and dependent-field generation.
  • Supports composable stages, column dependencies, validators and quality checks.
  • Supports multi-model workflows and model routing across generation stages.

Cons

  • Data Designer orchestrates generation but does not host the underlying models, so output quality depends partly on the configured model endpoint/provider.
  • Complex datasets can require careful design of prompts, column dependencies, constraints and validators.
  • Overloading a single generation call with schema, diversity, content and quality requirements can reduce output quality.
  • Generated text can still contain incorrect, hallucinated or logically inconsistent information.
  • Schema compliance does not automatically mean the generated dataset preserves the desired statistical distribution.
  • Provider availability, API behaviour and rate limits can affect a generation workflow.
  • Different underlying models can produce noticeably different datasets from the same high-level configuration.
  • Quality checks and validators must still be designed for the intended use case rather than assuming generated records are automatically correct.
Google Simula

Google Simula — Estimated Pros and Cons

Pros

  • Explores reasoning-first synthetic dataset design rather than only learning a distribution from an existing table.
  • Useful when dataset coverage, complexity and quality need to be deliberately designed.
  • Provides a different research direction from conventional tabular GAN and diffusion generation.
  • Can be useful for constructing training or evaluation scenarios from first-principles mechanisms.

Cons

  • Dataset quality depends strongly on the reasoning capability of the underlying model.
  • Reasoning errors can propagate into the generated dataset design.
  • A carefully designed mechanism can still encode incorrect assumptions about the target domain.
  • Because the approach can be seedless, its generated distribution is not simply learned from a real reference table.
  • Domain-specific generation requires careful specification of desired coverage, complexity and quality.
  • Poorly defined target characteristics can produce a well-structured dataset that represents the wrong problem distribution.
  • Generated examples still require downstream validation; reasoning-based generation does not automatically guarantee real-world validity.
  • Direct comparison with CTGAN/TabDDPM-style real-to-synthetic fidelity testing is less straightforward because the generation objective is different.
MOSTLY AI

MOSTLY AI — Estimated Pros and Cons

Pros

  • Provides a dedicated synthetic-data workflow focused on structured/tabular data.
  • Can reduce the amount of custom model engineering needed compared with building a generator from scratch.
  • Includes privacy-oriented mechanisms and model quality reporting.
  • Platform-oriented tooling can simplify end-to-end synthetic-data workflows.

Cons

  • Rare-category protection can replace uncommon values with _RARE_, intentionally removing some original detail.
  • Using sampled replacement for rare categories can alter the original categorical distribution by increasing frequencies of non-rare values.
  • Privacy protection and statistical accuracy can therefore involve a trade-off.
  • High-cardinality categorical columns and noisy categories require careful preparation and encoding choices.
  • Incorrect encoding can create invalid synthetic values, such as treating categorical numeric codes as continuous measurements.
  • Incorrectly formatted datetime fields can be interpreted as categorical values.
  • Bivariate relationships between columns can become weakened or lost in synthetic data.
  • Extreme-value privacy protection can intentionally remove unusual numerical or datetime cases before training, so some edge cases may not appear in the synthetic output.
